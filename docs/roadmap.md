## Fase 4 — Secco.LogStream (produto de referência, reescrito do zero)

> sobre SharedKernel + SDK, com histórico novo nos padrões da plataforma. O RS.Logging
> ([rafsecco/RS.Logging.API](https://github.com/rafsecco/RS.Logging.API)) serviu de referência
> funcional até a paridade, atingida no fechamento desta fase.
> Mudanças estruturais da reescrita: tenancy real (database-per-tenant via SDK — sem coluna
> `TenantId`, sem "sem header vê tudo"), Guid v7 (permite ingestão 100% assíncrona inclusive do

- [x] 4.1 Fundação: 4 camadas (ADR-0002) + `AddSeccoPlatform()` + OpenAPI/Scalar (DEV) + `openapi.json` versionado com teste de contrato (drift falha o CI; atualização via `SECCO_UPDATE_OPENAPI=true`) + `LogStreamDbContext` por tenant + migrations SQL Server (aplicadas no startup só em DEV) + Testcontainers provando isolamento entre bancos de tenant + CI com path filters (ADR-0014); `ITenantCatalog` ganhou `ListAsync()` (SDK v0.2)

## Fase 6 — Secco.SecureGate

> Arquitetura na ADR-0022: OpenIddict + ASP.NET Identity, identidade como dado de plataforma
> (banco próprio `secco_securegate` com usuários/roles/permissions por tenant, clients OIDC e
> catálogo de tenants); client credentials primeiro.

- [x] 6.1 Nasceu do template (prova real do padrão — inclusive achou e corrigiu um bug do template: descoberta do snapshot pós-mudança dos testes) + banco de plataforma `secco_securegate`: Identity + OpenIddict (entidades próprias com nomes curtos e chave Guid) + migrations nos 2 engines com **ADR-0017 completa** (`tb_users`, `id_pk_user`, `fl_email_confirmed`, `id_pfk_*` na associativa, `tb_oidc_*` — provado por testes de schema), `Tenant` do catálogo com FKs de users/roles, role único por tenant (ADR-0021); Client NSwag fora da solution até o 1º contrato (6.3)
- [x] 6.2 Client credentials + JWKS/discovery: OpenIddict server (`/connect/token` passthrough, JWT puro sem criptografia de conteúdo — produtos validam com `JwtBearer` padrão), certificados por ambiente (dev automático; **Production sem certificado não sobe**), scopes por produto via **seed de referência** (estreia da ADR-0019) + client/tenant demo em seed de DEV; **E2E cross-produto provado**: LogStream aceita token emitido pelo SecureGate via JWKS (tenant via `X-Tenant-Id`, o cenário interno da ADR-0005) e rejeita token forjado
- [x] 6.3 Catálogo de tenants servido pelo SecureGate: `TenantDatabase` por (tenant, produto) — database-per-tenant É por produto (ADR-0005); API de gestão write-only para segredos (scope `securegate:admin`) + API de catálogo com **scope por produto** (`catalog:<produto>`, least privilege ADR-0020 — a única superfície que entrega connection strings); `Secco.SecureGate.Client` nasceu (NSwag + `SecureGateTenantCatalog : ITenantCatalog` com client credentials automático, cache TTL curto e **stale em falha**; decisão lazy por configuração — sem a seção `Secco:SecureGate`, DEV segue no catálogo por configuração; parcial = fail-fast); SDK ganhou o middleware de exceções de tenancy (tenant desconhecido → 400, catálogo indisponível → **503 + Retry-After**); LogStream adotou e o E2E prova: **zero tenants em configuração** — migrations e requests resolvem pelo SecureGate, e desativar tenant propaga em ≤ 1 TTL
- [x] 6.4 `AddSeccoAuthorization()` (ADR-0021): policies dinâmicas por permissão (`RequireAuthorization("recurso:acao")` — formato canônico validado pelo `SeccoPermissions` do kernel; **constantes vivem em cada produto**, desvio consciente da letra da ADR-0021 pela regra de admissão da ADR-0003), cache `(tenant_id, role)` TTL curto **estrito e fail-closed** (sem stale — autorização nunca falha aberta), resolver por configuração em DEV/testes e remoto via `Secco.SecureGate.Client` (scope único `authorization:read`); **clients OIDC ganharam roles** (`ds_roles` — máquinas usam o MESMO modelo Role+Permission dos usuários, claim curta `role` no client credentials); SecureGate ganhou gestão de roles/permissões por tenant (PUT idempotente, scope admin) e endpoint de resolução; pipeline reordenado (tenancy ANTES de authorization — o tenant precisa existir quando as policies avaliam); LogStream adotou (`log-entries|log-processes|api-call-logs : read|write`) e o E2E prova: **revogar permissão propaga em ≤ 1 TTL com o mesmo token ainda válido** — a razão de ser da ADR-0021
- [x] 6.5 Login de usuário: **authorization code + PKCE obrigatório** + refresh token (ADR-0022). ASP.NET Identity via `AddIdentityCore` com cookie **não-default** (o padrão da API segue JwtBearer — ADR-0007) + telas Razor (Login, self-contained, antiforgery, sem assets externos); endpoints `/connect/authorize` (desafia o cookie → login → emite o code), `/connect/userinfo`, `/connect/logout` (end-session) — `TokenEndpoints` estendido para authorization_code/refresh **re-derivando claims do banco a cada emissão** (usuário desativado/role alterado reflete no refresh, ADR-0020); email/username **único global**, tenant vem do registro (decisão da 6.1 — sem seletor de tenant); usuários **provisionados por admin** (`POST /api/v1/tenants/{id}/users`, scope `securegate:admin`, hash do Identity, sem auto-registro; senha nunca volta) + roles atribuídos por tenant; consent **implícito** para first-party (tela adiada até client de terceiros — YAGNI); seed de DEV ganhou usuário demo + client web (PKCE); E2E prova o fluxo real do navegador (desafio → login antiforgery → code no redirect → troca com `code_verifier` → claims curtas no access token → userinfo → refresh; verifier errado = 400)

**Fase 6 concluída** — SecureGate cobre client credentials (máquinas), catálogo de tenants, autorização Role+Permission e login de usuário. O quarteto SharedKernel + SDK + LogStream + SecureGate provou o padrão da plataforma.

## Incrementos pós-Fase 8

- [x] SecureGate — **cifragem das connection strings de tenant no banco de plataforma** (ADR-0025, 2026-07-19): o catálogo custodiava a connection string de cada par (tenant, produto) em texto claro na coluna `ds_connection_string` — a disciplina write-only (ADR-0020) protege API, logs e erros, mas backup, dump ou acesso SQL direto ao banco de plataforma expunha as credenciais de **todos os tenants e produtos de uma vez**. Escolhida cifragem **AES-256-GCM na camada de aplicação**, não na infra: a plataforma é adotável on-prem via NuGet e não controla a infra do adotante, e o PostgreSQL (2º provider, ADR-0018) não tem TDE nativo — TDE/disco cifrado seguem **recomendados como defesa em profundidade**, não como a garantia. Implementação por **value converter do EF Core** no `SecureGateDbContext` (nenhum caminho do contexto persiste plaintext; o domínio segue puro — cifragem é preocupação de Infrastructure). Formato versionado e autodescritivo `secco-enc:v1:<base64(nonce ‖ ciphertext ‖ tag)>`; valor sem o prefixo é tratado como legado em claro, aceito na leitura e **re-cifrado por seeder idempotente no startup** (`TenantDatabaseReEncryptionSeeder`, mesma disciplina do seed de referência da ADR-0019) — upgrade sem migração manual. A coluna passou de 2000 para 4000 caracteres (o teto de 2000 continua valendo para o **plaintext**, no domínio). Chave mestra em `SecureGate:Catalog:EncryptionKey` (32 bytes, base64): **ausência em Production é fail-fast** no startup e a `DevelopmentEncryptionKey` embutida é **proibida em Production**, espelhando o padrão da `DevelopmentSigningKey` (ADR-0022). Rotação suportada pelo versionamento — `RetiredEncryptionKeys` só decifram, e o re-encrypt do startup converge tudo para a chave ativa. - [x] **Provisionamento de banco de tenant** (issue [#3](https://github.com/rafsecco/secco-platform/issues/3), **ADR-0028**, 2026-09-05): a plataforma decidiu database-per-tenant na ADR-0005 e nunca teve como criar esses bancos — o único `CREATE DATABASE` do monorepo estava na infraestrutura de testes, e o catálogo cadastrava a connection string de um banco criado por fora. Na prática os exemplos usavam `sa`, e **enquanto a connection string de um tenant usa um usuário amplo o isolamento da ADR-0005 é convenção, não garantia**: um erro de connection string alcança o banco do vizinho. A #4 destravou o dono (2026-09-04) e a ADR-0007 do `secco-intranet` já dizia onde: capacidade **da plataforma**, no SecureGate, que já é o registro de (tenant, produto) → banco e já custodia a connection string cifrada (ADR-0025). **Dois modos, os mesmos artefatos.** O modo **script** está sempre disponível e é o default — o SecureGate gera o SQL e um DBA aplica; o modo **automático** é opt-in por configuração e, sem credencial declarada, simplesmente não existe (fail-closed). A razão é de adoção, não de elegância: muitos DBAs corporativos jamais concedem `dbcreator` a uma aplicação, e um recurso que só funcionasse com esse privilégio não serviria a esses adotantes — já o script serve, e serve com privilégio mínimo por construção. O script devolvido é **exatamente** o texto que a execução automática aplica, para os dois caminhos não divergirem. **Execução síncrona, contrariando a opção que eu mesmo havia proposto**: enfileirar num job (Hangfire, que o SecureGate não tem) não entregava a segurança que aparentava — a credencial fica no mesmo processo de qualquer forma, e a assincronia moveria *quando* ela é usada, não *onde* mora; o que protege é opt-in + gate `securegate:admin` + conexão isolada existente só na operação, e repetir DDL automaticamente é mais perigoso que útil. A divergência foi levantada antes de implementar e ratificada. **O teto do que se concede é `db_owner` no próprio banco e nada no servidor** — DDL é necessário porque cada produto roda as próprias migrations; mais que isso, não. **Identificadores por allowlist estrita** (`^[a-z][a-z0-9_]{2,62}$` + recusa de nomes de sistema + delimitação com escape), aplicada **antes** de qualquer concatenação: nome de database e de login não podem ser parametrizados em DDL, então esta é a única barreira entre um nome vindo da requisição e um comando executado com privilégio de administrador do servidor. **Segredo gerado no servidor** (aleatório criptográfico, alfabeto que não quebra connection string nem literal SQL), exibido **uma única vez** dentro do script — por necessidade de quem aplica — e persistido só cifrado; a connection string nunca volta em resposta. Reprovisionar responde **409**: apagar o acesso vigente em silêncio seria pior que recusar. Entregue junto o **painel de estado dos bancos** (`GET /api/v1/tenants/{id}/databases/status`), que não usa credencial privilegiada nenhuma — sonda cada banco com a conexão de runtime do próprio tenant e responde alcançável/inalcançável com classificação de falha, nunca com a exceção crua. **O `docker-compose.yml` deixou de ensinar `sa`**: um `docker/sqlserver-init.sql` cria os seis bancos de desenvolvimento e, para cada um, um login próprio com `db_owner` apenas nele — o mesmo modelo que o endpoint produz. Verificado à mão contra o container: o login do tenant alfa abre o próprio banco, **não** abre o do beta e **não** consegue `CREATE DATABASE`. **Três defeitos encontrados na revisão do próprio código**, todos corrigidos com teste: a retenção de auditoria (entrega anterior) cortava pelo `OccurredAt` **declarado pelo chamador** — um valor forjado no passado apagaria a trilha antes da hora, e passou a cortar pelo `CreatedAt` do servidor; o helper `GetConnectionStringFor` sufixa todo nome de database, então pedir `"master"` devolvia `master_<sufixo>` e produzia um 500 opaco; e `Guid.CreateVersion7()` fatiado no início gera valores iguais para guids do mesmo milissegundo (v7 começa com timestamp), o que fazia slugs de teste colidirem. Corrigida de passagem a classificação do erro 4060 do SQL Server, que era reportado como "servidor inacessível" quando significa "banco inacessível para este login" — diagnósticos bem diferentes para quem opera. Fora de escopo, registrado: PostgreSQL (rodada seguinte, abstração pronta), rotação de senha de banco, desprovisionamento, aplicação de migrations pelo SecureGate e tela no AdminPortal. Verificado: build sem avisos, **192 testes no SecureGate** (146 antes) e **637 na solution inteira**, todos verdes (`dotnet test Secco.Platform.slnx`). Além dos automatizados, isolamento verificado à mão contra o container: o login do tenant alfa abre o próprio banco, recebe `Cannot open database ... Login failed` no banco do beta e `CREATE DATABASE permission denied` no master; e o LogStream sobe respondendo `200` em `/health/ready` com esse login.

- [x] **`operationId` estável em todo endpoint de contrato** (issue [#9](https://github.com/rafsecco/secco-platform/issues/9), 2026-09-05): achado comparando duas publicações da mesma leva — o `Secco.SecureGate.Client` 0.3.0 ganhou dois endpoints e saiu **aditivo**, enquanto o `Secco.LogStream.Client` 0.2.0 saiu **quebrando**. A variável era uma linha: sem `.WithName(...)` não há `operationId`, e o NSwag deriva o nome do método do **path**, produzindo `LogEntriesGETAsync`/`GET2Async`/`BatchAsync`. Esses nomes dependem de quantos e quais endpoints existem no documento, então **adicionar um endpoint renomeia métodos de outros** — foi o que quebrou o `ILogQueryService` do AdminPortal. `.WithName(...)` aplicado às 24 rotas que não tinham (16 no LogStream, 5 no NotificationHub, 3 no template), com nome verbo+recurso; contratos e clients regenerados; os dois consumidores internos corrigidos (`CreateLogEntryBatchAsync` no sink, `SearchLogEntriesAsync` no AdminPortal). **A causa raiz também foi corrigida**: o esqueleto de endpoint da skill `secco-platform-standards` não tinha `.WithName()`, e por isso todo endpoint novo nascia com o defeito — agora tem, com a explicação. O template entrou por ADR-0013 (divergência entre template e padrão é bug). Feito **agora** de propósito: renomeia os métodos uma última vez, e depois do nuget.org público cada endpoint novo passaria a arriscar quebrar consumidor que não é mais nosso.

- [x] **NotificationHub: segundo provider de e-mail e despacho em lote** (issues [#14](https://github.com/rafsecco/secco-platform/issues/14) e [#15](https://github.com/rafsecco/secco-platform/issues/15), 2026-09-05): duas demandas do adotante entregues juntas, por tocarem o mesmo produto e caberem numa regeneração de contrato só. **#14** — `IEmailSender` tinha uma implementação só, SMTP, e quem sobe em nuvem sem servidor de e-mail simplesmente não enviava. A porta já estava na camada certa desde a Fase 8, então a entrega é o que a issue previa: um implementador a mais (`SendGridEmailSender`, sobre `ISendGridClient` para ser testável sem conta e sem rede) e a seleção por configuração, na mesma forma do provider de banco (ADR-0018) — enum do produto, default explícito, escolha na composição. A configuração passou a ser **validada no startup**: sem isso, provider pela metade só falharia dentro de um job, com notificação já represada como `Pending` e o retry do Hangfire mascarando a causa. **#15** — `CreateNotification` criava uma por chamada, e uma publicação para 500 pessoas eram 500 requisições. A forma escolhida foi **um conteúdo, N destinos**, e não uma lista de N notificações completas: o caso real é uma publicação única alcançando um público, e repetir título e mensagem por destinatário mandaria o mesmo texto centenas de vezes pela rede. **Achado que mudou o desenho**: `AddAsync` faz `SaveChanges` por notificação, então um lote em laço trocaria N chamadas HTTP por N idas ao banco — quase nada. As portas ganharam `AddRangeAsync`, e é isso que faz o endpoint valer mais que o laço do chamador. Validação é **tudo-ou-nada** com a posição do destino inválido apontada: gravar os válidos e reportar o resto deixaria o chamador sem saber o que repetir, que é exatamente a dor da issue. O que continua sendo N é o enfileiramento — um job por destino de e-mail, de propósito, para preservar o retry por notificação da Fase 8; daí o teto configurável de 500 destinos por lote (ADR-0020). De passagem, a validação de entrada foi extraída para `NotificationInputRules`, separada em **conteúdo** e **destino** — sem essa divisão o lote duplicaria a regra, e regra duplicada diverge. A **#13** (canal Teams/Slack) ficou para rodada própria, com canal por ferramenta decidido e ADR prevista: ela abre o conjunto fechado de canais, que é invariante declarada do produto.

- [x] **NotificationHub: canais externos de comunicação corporativa** (issue [#13](https://github.com/rafsecco/secco-platform/issues/13), **ADR-0029**, 2026-09-05): a demanda abria uma invariante declarada do produto — o conjunto fechado de canais — e por isso veio com ADR antes de código. **A validação externa inverteu uma premissa comum**: os Office 365 Connectors do Teams foram desativados entre 18 e 22 de maio de 2026, então o webhook clássico não existe mais e o caminho é Power Automate Workflows com Adaptive Card; já os incoming webhooks do Slack seguem suportados, sem aviso de descontinuação. As duas ferramentas não são o mesmo problema com URL diferente. `teams` e `slack` entram como canais **nativos**, e o conjunto **continua fechado** — a ADR acrescenta dois membros, não abre para extensão arbitrária. Não há canal `webhook` genérico e **a URL nunca vem no payload**: o consumidor pede um canal, o Hub resolve o destino. O contrário seria proxy HTTP dirigido pelo consumidor, SSRF por construção. Configuração **por tenant, no banco do próprio tenant** — por instalação faria notificação de um tenant chegar ao canal de outro numa instalação multi-tenant. O destino é cifrado em repouso com o cifrador que subiu para o SDK, e a superfície é write-only: o `GET` devolve canal, estado e datas, nunca a URL. Validação de destino recusa não-HTTPS, loopback, faixa privada e link-local (inclusive `169.254.169.254`) — defesa em profundidade sobre a barreira arquitetural. `Notification` foi **generalizada com discriminador de canal** em vez de ganhar entidade por canal: o critério é o mesmo que a Fase 8.4 usou para separar o `InAppNotification` — ciclo de vida. Lá era diferente e por isso separou; aqui e-mail, Teams e Slack têm o mesmo, e por isso junta. **A migration toca tabela com dado existente**: `ie_channel` entra com default `0`, que é `NotificationChannel.Email`, para que toda notificação anterior continue significando o que significava — e há teste travando esse valor do enum, porque reordená-lo corromperia o histórico. Entrega assíncrona com retry por entrega, reusando a máquina do e-mail; job separado do `SendEmailJob` de propósito, porque jobs já enfileirados no Hangfire referenciam o tipo pelo nome e renomear orfanaria o que estivesse em voo. **Achado durante a implementação**: canal externo dentro de um lote não pode entregar N vezes — uma publicação que alcança 500 pessoas por e-mail deve postar **uma** mensagem no canal da empresa, e o lote passou a criar uma entrega por canal, não por destino. Fora de escopo, registrado: Bot/Teams App (identidade própria em vez de Flow bot), `chat.postMessage` do Slack, Google Chat, e tela no AdminPortal.

- [x] **NotificationHub: consulta de status em massa** (issue [#23](https://github.com/rafsecco/secco-platform/issues/23), 2026-09-06): o problema de N reaparecendo do lado da **leitura**, logo depois de a #15 tê-lo resolvido do lado da escrita — despachar para 500 pessoas virou uma chamada, e descobrir quais falharam continuava sendo quinhentas. **A investigação invalidou a premissa da própria issue**, que propunha filtrar pelos campos `Source`/`Type` já existentes: a entidade `Notification` **não os guardava**. Os dois handlers de despacho aceitavam esses campos, validavam o tamanho deles — inclusive num despacho só de e-mail — e depois os passavam apenas para o `InAppNotification`, descartando-os na `Notification`. Campo validado e jogado fora é defeito, não lacuna, então a correção entrou junto: `ds_source` e `ds_type` na `tb_notifications`, alimentados pelos dois caminhos de despacho. Escolhido gravar os campos em vez de um `BatchId` gerado pelo Hub porque serve o endpoint unitário e o lote igualmente, responde tanto "como foi a publicação X" (`type` = id dela) quanto "tudo do mural nos últimos 30 dias" (`source` = mural), não muda o contrato de resultado do lote, e para de fazer as duas entidades discordarem sobre os mesmos dois campos da mesma requisição. `GET /api/v1/notifications` espelha o `SearchLogEntries` do LogStream: filtros combinados por AND, `PageRequest` do kernel (que já limita a página a 200, o controle de negação de serviço), mais recentes primeiro. **Filtro de campo estruturado usa igualdade, nunca `LIKE`** — mesma decisão que o LogStream tomou para `ServiceName`/`Category`. **Dois pontos de segurança (ADR-0020)**: o filtro é input externo indo para uma cláusula `WHERE`, então tem teto de tamanho como a escrita tem; e o teto do schema virou constante do domínio (`Notification.SourceMaxLength`), com a configuração podendo **apertar** o limite e nunca afrouxá-lo — sem esse `Math.Min`, um `MaxSourceLength` configurado acima da coluna passaria na validação e estouraria no `INSERT`, virando 500 em vez de erro de validação. **Achado na revisão da implementação**: sem tamanho explícito o EF encolhia a coluna indexada para `nvarchar(450)`, que é o máximo que cabe na chave de índice do SQL Server e não uma decisão de modelagem — a plataforma já tinha o padrão certo (constante na entidade, como `ChannelConfiguration.ChannelMaxLength`), e o `InAppNotification` com `nvarchar(max)` era o caso desleixado, não o modelo. Migrations nos dois engines, contrato e client regenerados no mesmo PR. Verificado: build sem avisos e **682 testes verdes** na solution inteira (`dotnet test Secco.Platform.slnx`).

- [x] **Entrega agendada de notificação** (issue [#24](https://github.com/rafsecco/secco-platform/issues/24), 2026-09-07): todo despacho era imediato, e a lacuna atravessava duas camadas — o `IBackgroundJobScheduler` do SDK tinha uma operação só (`Enqueue`), então o Hub não tinha como oferecer o que o Hangfire já faz nativamente. O SDK ganhou `Schedule(..., DateTimeOffset enqueueAt)` ao lado do `Enqueue`, e o `TenantJobRunner` **não mudou**: o tenant continua sendo restaurado antes do job, agendado ou não. **O achado que mudou o escopo foi o canal in-app**, que a issue não tratava: diferente do e-mail, ele não tem job de entrega — o `InAppNotification` é gravado no despacho e a consulta de não lidas filtrava só por `UserId` e `!IsRead`. Com agendamento, o item apareceria no inbox na hora, avisando sobre um comunicado que o mural ainda não mostra — exatamente a saída que a própria issue descarta. Resolvido com **estado derivado do relógio, sem job de transição**: `ScheduledFor` na entidade e a consulta de não lidas exigindo `ScheduledFor is null OR <= agora`. É o mesmo princípio que o adotante já adotara no Mural e que a issue cita com aprovação, e mantém a linha existindo desde o despacho, então dá para mostrar "programado para" antes da entrega. O gate entrou **nas duas** consultas, lista e contagem: só na lista, o sino exibiria contagem de itens que o usuário não consegue abrir. **Duas decisões de comportamento, tomadas explicitamente porque a issue as deixou em aberto.** Data no passado **não** é erro: vira entrega imediata, que é o que o Hangfire já faz, e recusar criaria modo de falha por diferença de relógio entre chamador e servidor. E entrou um **teto de horizonte** (`MaxScheduleHorizonDays`, 365) que a issue não pedia: o storage do Hangfire fica no banco de **plataforma**, compartilhado entre tenants (ADR-0015), então agendamento sem limite deixa um chamador acumular jobs indefinidamente em infraestrutura comum — negação de serviço, não só desperdício (ADR-0020). `ScheduledFor` aparece nos dois DTOs e virou filtro por range no `SearchNotifications` da #23, respondendo as duas perguntas de escopo que a issue fez. O índice existente do inbox foi **estendido** (`user_id, fl_read` → mais `dt_scheduled_for`) em vez de duplicado, com o `Down()` restaurando o anterior. Migrations nos dois engines, contrato e client regenerados no mesmo PR; nenhum método do client mudou de nome. Fora de escopo, registrado: `GetByIdAsync` do inbox não tem gate de tempo, então quem já tem o id (só o próprio despachante) consegue marcar como lido um item ainda invisível — consistente com o modelo de "chamador confiável informa o `userId`" que já está no backlog, e não um furo novo. Verificado: build Release sem avisos em código de produto e **697 testes verdes** na solution inteira (`dotnet test Secco.Platform.slnx`).

- [x] **Clients de produto com client credentials** (issue [#25](https://github.com/rafsecco/secco-platform/issues/25), 2026-09-09): `AddLogStreamClient()` e `AddNotificationHubClient()` registravam o `HttpClient` só com a URL base, enquanto **todos** os endpoints dos dois produtos exigem permissão — o client compilava, injetava e tomava 401 na primeira chamada, e o adotante remontou a composição à mão duas vezes. **A decisão estrutural foi onde as peças de credencial passam a morar.** O `SeccoClientCredentialsHandler` estava no `Secco.SDK.AspNetCore`, que arrasta Hangfire.Core, Hangfire.SqlServer, Hangfire.AspNetCore e JwtBearer; fazer os clients referenciarem aquele pacote poria Hangfire em qualquer consumidor, inclusive num worker de console que só quer disparar uma notificação — contrariando na prática a promessa de "produtos adotáveis de forma independente". Nasceu o **`Secco.SDK.ClientCredentials`**, fino de propósito. É a **segunda** promoção destas mesmas peças: o handler já havia subido do `Secco.SecureGate.Client` para o SDK pelo mesmo raciocínio, e as options tinham ficado para trás — agora vieram junto; de quebra, quem usa só o `Secco.SecureGate.Client` deixa de carregar Hangfire. **Pré-requisito que a issue não mencionava e que sozinho invalidaria a entrega**: o SecureGate **não conhecia o NotificationHub** — a API dele valida audience `secco-notificationhub` e o seed de referência mapeava scope→resource só para `logstream` e `securegate`, então não existia scope capaz de produzir um token que ele aceitasse. Acrescentado `notificationhub` ao seed de referência (ADR-0019, todos os ambientes, idempotente) e ao grant do console de DEV; **não** ao `CatalogProducts`, porque o produto não consome o catálogo do SecureGate e scope sem consumidor é superfície à toa. **Decisão que contraria o pedido da issue**, registrada: `BaseUrl` vazia continua lançando — configuração ausente virando no-op troca erro de startup por `NullReferenceException` em runtime; o que ficou opcional foram as **credenciais** (ausentes = sem handler, serve DEV; parciais = fail-fast, ADR-0020). **Dois defeitos achados na revisão.** O primeiro foi de especificação minha: batizei a chave nova de `IssuerBaseUrl`, mas o sink do `Secco.SDK.Logging` já ocupava a **mesma seção** `Secco:LogStream` com `AuthorityUrl` para o mesmo conceito — quem configurasse uma teria o sink autenticado e o client não, meia-configuração silenciosa, exatamente a classe de erro que esta issue existe para eliminar; renomeado para `AuthorityUrl` em tudo. O segundo é **pré-existente e independente da issue**: `Microsoft.SourceLink.GitHub` 8.0.0 arrastava `Microsoft.Build.Tasks.Git` 8.0.0 com CVE moderada, e com `TreatWarningsAsErrors` o `NU1902` virava erro que travava o build de **todo** projeto empacotável, o SharedKernel incluído. Desde o .NET 8 o SourceLink é parte do SDK: a referência explícita saiu, e ficou provado que ele continua valendo — o nuspec mantém `repository` com o SHA e o `.snupkg` segue sendo gerado. Segunda vez que um pin de segurança envelhece aqui (a primeira foi o `NU1903` do `System.Security.Cryptography.Xml`), o que confirma que reavaliar pin é manutenção periódica, não evento único. O vigia `release-pendente` da entrega anterior detectou o pacote novo como "nunca publicado" e confirmou o prefixo registrado no workflow — validação prática dele na primeira oportunidade. Verificado: build Release sem avisos em código de produto e **719 testes verdes** na solution inteira (`dotnet test Secco.Platform.slnx`).

Consolidado em 2026-08-30. Antes disso, os itens técnicos viviam dentro das entradas de fase e das consequências das ADRs — encontráveis só por quem já sabia que existiam.

### Demandas de adotante (abertas como issue, 2026-09-02)

O canal de demanda passou a ser **GitHub Issues com a label [`adopter-demand`](https://github.com/rafsecco/secco-platform/issues?q=is%3Aissue+label%3Aadopter-demand)** — antes, o que um adotante precisava vivia como prosa neste arquivo, sem lugar para discutir nem para acompanhar. A discussão de cada item acontece na issue; o roadmap só aponta.

A **#1 e a #2 foram entregues juntas** (ver o incremento correspondente acima). Elas foram agrupadas por decisão explícita: pôr o nome do serviço em coluna própria, em vez de prefixo na mensagem, já obrigava migration nos dois engines e regeneração de contrato — exatamente o custo que a #2 também pagaria.

**A #4 teve o modelo definido em 2026-09-04** ([discussão registrada na issue](https://github.com/rafsecco/secco-platform/issues/4#issuecomment-5549419595)). O que travava não era UI nem código: era o significado de "administrar todos os tenants". A resposta é que **cada instalação é soberana** — a Intranet é um produto que empresas baixam e rodam por conta, e a multi-tenancy existe para que a empresa desenvolva **outros produtos seus** sobre SecureGate e LogStream. Não é o portal da Secco; é o portal da empresa que adotou. Decorrências:

- **O `Secco.AdminPortal` permanece, com papel redefinido**: console mínimo para quem adota a plataforma **sem** a Intranet. Preserva a promessa de "produtos adotáveis de forma independente" (primeira linha do `CLAUDE.md`), que aposentá-lo quebraria. A Intranet é o portal completo da empresa que a usa; a duplicação de telas entre os dois é real, bounded e é o preço daquela promessa.
- **"Duas identidades" encolheu**: sob esta leitura não são identidades de mundos diferentes, é hierarquia dentro de uma instalação (admin de instalação × admin de tenant) — o modelo `cluster-admin`/`namespace-admin`. `platform-operator` e "tenant de plataforma" passam a significar **operador desta instalação**; o modelo serve, o nome engana.
- **Elevação explícita resolve o token, sem tocar em ADR nenhuma**: para ler log cross-tenant, a aplicação pede ao SecureGate um **segundo token** — sem `tenant_id`, escopo só `logstream`, só leitura, TTL curto, sem refresh —, usado apenas naquela área e descartado ao sair. Privilégio como **ato**, não como estado; formato inspirado no [RFC 8693](https://www.rfc-editor.org/rfc/rfc8693) para não inventar protocolo (o adotante planeja pentest).
- **Descartadas** as alternativas 2 (aposentar o AdminPortal) e 3 (CLI). Dois fatos pesaram: os front-ends não são o mesmo stack (Intranet é MVC, AdminPortal é Blazor Server — "migrar" seria reescrever), e o AdminPortal tem 1222 linhas sem domínio nem banco, mais barato manter que reescrever como CLI.
- **A #3 sai destravada com dono definido**: a ADR-0007 do `secco-intranet` já determina que criar database, criar login e conceder permissão são capacidades **da plataforma**, que custodia o catálogo cifrado (ADR-0025). O provisionamento vive no **SecureGate**, não no portal — e aí qual UI o chama volta a ser detalhe reversível.
- **ADR pendente**: a decisão afeta 2+ produtos e é difícil de reverter, então merece ADR própria. Escrevê-la quando a área administrativa da Intranet começar, para nascer ancorada em código e não em intenção.

### Produtos (só após a fundação amadurecer)

Nenhuma ADR define escopo real para estes; detalhar via rounds de design (como foi o NotificationHub) só quando a vez de cada um chegar.

- **Configuration** — configuração dinâmica por tenant (valores operacionais, não binários como feature flags) sem precisar de redeploy; um catálogo central de settings por tenant/produto, análogo em espírito ao catálogo de tenants do SecureGate.
- **FeatureFlags** — ativação/desativação de funcionalidades em runtime, por tenant (ou por %, por role); controla rollout gradual e kill-switch de feature sem deploy.
- ~~**Audit**~~ — **resolvido sem virar produto** (2026-09-03). A decisão de forma da [#2](https://github.com/rafsecco/secco-platform/issues/2) foi **recurso novo dentro do LogStream** (`AuditEntry`), não `Secco.Audit` separado: um produto de quatro camadas inteiro — banco, migrations nos dois engines, client, CI, Docker — para uma única entidade não se justificava, e o LogStream já tinha os dois providers, o client publicado e a leitura cross-tenant do operador. `Secco.Audit` sai desta lista.

*Regra de ouro: ficam no backlog até a fundação estar madura. Paralelizar produtos impede que qualquer um amadureça.*

**O que destrava a decisão (registrado em 2026-09-01).** O primeiro adotante real da plataforma é o **`secco-intranet`** ([rafsecco/secco-intranet](https://github.com/rafsecco/secco-intranet)), repositório standalone que consome cinco pacotes por `PackageReference` — `Secco.SharedKernel` 0.3.3, `Secco.SDK.AspNetCore` 0.4.1, `Secco.SDK.EntityFrameworkCore` 0.1.0, `Secco.SecureGate.Client` 0.2.1 e `Secco.SDK.Testing` 0.1.0 —, o que põe o caminho de adoção externa do [`getting-started.md`](getting-started.md) em uso real. O roadmap dele é hoje a melhor fonte de demanda para decidir o próximo produto, e o que ele diz é: **`Configuration` não aparece nenhuma vez**, e **`Audit` aparece uma vez só**, na Fase 4, como *"Analytics/auditoria mais robusta em cima do LogStream"* — enquadrada como **uso do LogStream**, não como produto novo. O que está aberto e próximo lá é consumir o que já existe (`Secco.LogStream.Client` na Fase 0, canal in-app do NotificationHub na Fase 1). Portanto o gatilho de ambos os produtos é **uma lacuna que o adotante bata de fato**; para o `Audit` especificamente, o experimento barato vem antes do produto — usar o log de processos + auditoria que o LogStream já tem e ver onde não serve, que foi como o escopo do NotificationHub se definiu.

**Atualização de 2026-09-02 — o adotante olhou e reportou ([#2](https://github.com/rafsecco/secco-platform/issues/2)).** O que o LogStream tem hoje **não** serve para trilha de usuário, por duas razões estruturais: `LogEntry` não tem campo de ator (só `Level`, `Message`, `StackTrace`, `CorrelationId`, `CreatedAt`), então "quem fez o quê" só caberia dentro do texto da mensagem, sem ser filtrável; e `LogProcess` — o candidato aparente — foi reservado pelo adotante a **processo de negócio com passos definidos**, cujo consumidor real é o motor de workflow da Fase 2 dele. Some-se a isso a retenção: auditoria vive anos e log de diagnóstico expira em dias, e o `LogRetentionWorker` de hoje é global. O `Configuration`, por sua vez, **segue sem demanda** — não apareceu nenhuma vez. E apareceram duas lacunas que nenhum item deste backlog cobria: provisionamento de banco de tenant ([#3](https://github.com/rafsecco/secco-platform/issues/3)) e a fronteira do console de operação ([#4](https://github.com/rafsecco/secco-platform/issues/4)).

### Decisões adiadas conscientemente

Diferentes dos itens acima: aqui o escopo já é conhecido e a decisão foi de não fazer agora.

- **Vínculo `userId` ↔ `sub` no inbox in-app do NotificationHub** (severidade baixa, ADR-0020). Hoje o modelo é "chamador confiável informa o `userId`": qualquer caller com `in-app-notifications:read`/`write` lê ou marca a inbox de outro usuário **do mesmo tenant**. O isolamento entre tenants está intacto. É decisão de design do produto, não fix mecânico.
- **Seção de federação no AdminPortal** (follow-up da ADR-0026) — a gestão de `TenantFederation` hoje existe só via API.
- **Desligar senha local para tenant federado** (follow-up da ADR-0026) — hoje login por senha continua valendo mesmo com federação habilitada.

### Evoluções técnicas com gatilho definido

Cada uma tem uma condição que a destrava; nenhuma é "quando sobrar tempo".

| Item | Gatilho |
|---|---|
| **Full-text search no LogStream** (hoje `LIKE`, ADR-0018) | demanda real de busca; implementação por provider |
| **Webhook e dashboard do LogStream** | demanda real |
| **Broker de mensageria** (ADR-0015 Camada 3) | caso real de multi-produtor/multi-consumidor; exige ADR nova |
| **OpenTelemetry** substituindo o `TraceId` manual (ADR-0008) | quando observabilidade distribuída passar a doer |
| **Envelope `ApiResponse<T>`** (ADR-0003) | só se o SDK provar caso real; hoje ProblemDetails + clients tipados bastam |
| **Fixture de paridade PostgreSQL no `Secco.SDK.Testing`** (ADR-0027) | duas cópias hoje; extrair "quando doer" |
| **Cofre externo de segredos** (Key Vault/Vault, ADR-0025) | adotante que exija; exige ADR nova |
| **LDAP contra AD on-premises** (ADR-0026) | adotante on-prem real; exige ADR nova |
| **App registration do Entra por tenant** (ADR-0026) | quando a app multi-tenant única não bastar; exige ADR nova |
| **Busca cross-tenant "todos de uma vez" no LogStream** (hoje é um tenant por vez via `X-Tenant-Id`, ADR-0024) | decidido em 2026-09-04 na [#4](https://github.com/rafsecco/secco-platform/issues/4); com database-per-tenant exige consultar N bancos e unir na aplicação, com paginação sobre a união — implementar quando a área de análise de log tiver dono |
| **Elevação explícita para leitura cross-tenant** (segundo token sem `tenant_id`, TTL curto, só `logstream:read`) | quando a área de análise de log sair do AdminPortal; formato inspirado no RFC 8693 |
| **`OnBehalfOfId` no `AuditEntry`** | junto com o "acessar como" ([#6](https://github.com/rafsecco/secco-platform/issues/6)) — decidir **antes** de a trilha ganhar volume: adicionar coluna a tabela com anos de retenção é mais caro depois |
| **Renomear o vocabulário de operador** (`platform-operator` → operador de instalação, ADR-0024) | junto com a ADR da fronteira do console; o modelo serve, o nome engana |
| **PostgreSQL no provisionamento de banco de tenant** (ADR-0028) | abstração pronta com um implementador; entra quando houver adotante com tenant em Postgres |
| **Rotação de senha de banco de tenant** (ADR-0028) | terceira operação privilegiada; hoje reprovisionar responde 409 |
